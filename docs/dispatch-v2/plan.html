Crewzo Dispatch Layer

Turning the existing browse-and-book marketplace into an admin-controlled dispatch system: broadcast job offers, worker interest, geo-verified site arrival, and a two-OTP work handshake.

Date 24 Aug 2026 Repo SmartWorker Status Approved to detail Author Claude + Hareesh

The short version

This is not a new set of software. Roughly 65% of what you described already exists in this repo — two Flutter apps, three backends, an admin portal, an SMS gateway. What you are actually asking for is a dispatch layer bolted onto the existing booking system, plus push notifications (which do not exist yet at all).

Building it as a fresh product set would mean re-writing auth, worker profiles, the admin portal and both apps for no gain. My recommendation is to extend Crewzo and version it as v2. That is roughly 9–11 weeks of build versus 6+ months greenfield.

Two things in your description will hurt you in production if built literally, and I have flagged both in §13: an admin gate on every booking, and broadcasting every job to every worker.

Four scope questions are now settled and folded in below — extend rather than rebuild, all three roles take work directly, filtered broadcast, and a flat service charge with wages left off-platform. That last one has consequences well beyond the payment screen; §9 works them through.

02 — The core change

From marketplace to dispatch

Today the customer picks a specific worker and a booking row is created against that worker immediately. Your new flow inverts this: the customer describes a need, and the worker is decided later, by admin, out of a pool of volunteers.

Those are two genuinely different objects, and cramming both into the existing bookings table is where this design goes wrong. The fix:

  • A job request is what the customer creates. Trade, date, duration, address with a map pin, notes, budget. It has no worker.
  • A job offer is one row per notified worker per request. This is the notification's audit trail — sent, seen, interested, declined, expired, admin-approved, admin-rejected.
  • A booking is created only when admin assigns a worker. It stays the record everything downstream already points at, so feedback and grievances keep working untouched.

Keeping the old direct-booking path alive alongside this is also possible — a customer who already trusts a particular worker skips the broadcast and goes straight to admin review. Worth having; costs almost nothing once the state machine exists.

04 — State machine

The full job lifecycle

Amber markers are the two admin gates you asked for. Nothing crosses them without a human decision.

Customer
submittedCustomer describes the job, drops a map pin, picks date and duration. No worker involved yet.
Admin
admin_review  — GATE 1Admin approves, edits, or rejects. Only on approval does anything reach a worker. Rejection returns a reason to the customer.
System
broadcastOne job_offer row per matched worker, agent and supervisor — filtered by trade, district and availability, ordered by rating and distance. Each row fires a push notification and an in-app popup. Offers carry an expiry, and admin has a widen-the-broadcast button.
Workers
collecting_interestEach recipient responds interested or declined. Silence becomes expired. Admin watches the count live.
Admin
assigning  — GATE 2Admin sees each interested worker beside their profile — trade, rating, past jobs, distance, documents — and approves exactly one. The rest are notified they were not selected.
System
assignedBooking row created. Start OTP generated and shown in the customer app on that booking. Worker gets the address and the pin.
Worker
en_routeOptional. Worker taps "on my way"; customer sees an ETA. One location sample logged.
Worker
in_progressWorker taps "start work". Server checks three things together: correct start OTP, device inside the geofence, and GPS accuracy good enough to trust. All three pass, or the start is refused with the specific reason.
Worker
worker_completedWorker marks the work done, optionally with photos. Completion OTP is generated at this moment — not earlier — and appears in the customer app.
Both
completedCustomer reads the completion OTP aloud, worker enters it. Location logged again. Job closes and payment settles.
Both
feedback_windowBoth sides rate each other. Ratings stay hidden until both submit or seven days pass — this is what stops retaliatory reviews.

Escape hatches you must build, not discover later

  • Nobody shows interest. Offer window expires with zero takers → admin is alerted, can widen the broadcast or call the customer. Without this, requests silently rot.
  • Customer absent at completion. They cannot read out an OTP they are not there to see. Worker raises "customer unavailable" → admin verifies by phone and force-completes, logged as an override.
  • Assigned worker no-shows. Admin un-assigns and re-opens the request to the remaining interested workers without a fresh broadcast.
  • Mid-job cancellation. Both sides need it, with a reason, and it must not corrupt the ratings.
05 — Notifications

Getting the popup in front of people

You need two delivery paths, because "popup" means different things depending on whether the app is open.

  • App in foreground — a WebSocket (or SSE) connection pushes the offer and the app renders a modal immediately. This is the real popup.
  • App backgrounded or killed — Firebase Cloud Messaging delivers a high-priority data notification. Tapping it opens the same modal. FCM is free at any volume you will hit.
  • No app, no data — the existing SMS gateway sends a short message. Kerala has coverage gaps, and older agents may not install anything.

One rule that matters more than the transport choice: a notification is a side effect of writing a job_offer row, never a standalone send. Push delivery is unreliable and duplicates happen. If the row is the truth and the push is only a nudge, a worker who missed the push still finds the offer waiting in their inbox, and you can prove afterwards who was told what and when.

Also notify on the admin decisions. A worker who taps "interested" and hears nothing for two hours assumes the app is broken. Push on approve, on reject, and on offer expiry.
06 — Geolocation

Proving the worker was on site

Three decisions carry this feature.

Checkpoints, not continuous tracking

Sample location at four moments — offer accepted, en route, work start, work complete — plus a low-frequency heartbeat while a job is in_progress and the app is open. Continuous background tracking costs you battery complaints, a Play Store background-location review with a mandatory video demo, and a privacy exposure you do not need. Checkpoints answer the actual question: was he there when he said he was.

The customer must drop a pin

A geofence needs coordinates. Today bookings hold a free-text address, which cannot be verified against anything. Adding a map pin step to the customer booking flow is a hard prerequisite — with flutter_map and OpenStreetMap it costs nothing in licensing. Suggested radius 120 m, tunable per job, because phone GPS in a dense Kerala town realistically lands within 10–50 m.

Treat GPS as evidence, not as a lock

Mock-location apps are trivial to install. Android exposes Position.isMocked — record it and flag the job to admin, but do not hard-block, because false positives will strand honest workers on real sites. Your genuinely strong control is the completion OTP: the customer physically has to hand it over. Geo catches sloppiness; the OTP catches fraud.

07 — OTP handshake

Two codes, two different jobs

 Start OTPCompletion OTP
CreatedOn assignmentOnly when worker marks the work done
Shown toCustomer, on that booking screenCustomer, on that booking screen
Entered byWorker, at the siteWorker, after the customer inspects
ProvesWorker actually arrived and met the customerCustomer saw the finished work and released it
Also checksInside geofence + GPS accuracy thresholdLocation logged; no gate
ValidityJob window ± 2 h30 min, regenerable by the customer

Non-negotiables on both: 6 digits, stored as a hash, bound to one booking id, capped at 5 attempts then locked pending admin reset, and — critically — never delivered to the worker through any channel. No SMS, no push, no email. The moment a code reaches the worker's device by itself, both controls are worthless.

08 — Feedback

Two-way ratings

The feedback table already exists for customer→worker. Add the reverse direction, and make both blind until either both parties have submitted or seven days elapse.

Worker ratings should then feed back into the broadcast: when a request goes out, order and prioritise recipients by rating, completion rate, and distance. That is what stops the highest-rated workers from drowning in offers they never see, and it is the cheapest quality lever you have.

09 — Revenue

How Crewzo gets paid

Decision taken: the customer pays Crewzo a service charge for the booking. Wages are negotiated and settled directly between customer and worker, off-platform, and per-worker rates come off the product entirely.

That is a clean, defensible model — you are selling dispatch and trust, not labour arbitrage. It also has four consequences that reach much further into the build than a payments screen, and each one needs deciding now rather than in phase five.

MoneyWho sets itWhere it flowsDoes Crewzo see it?
Service chargeCrewzo, by tierCustomer → Crewzo, on assignmentYes — the revenue
WagesNegotiated customer ↔ workerDirect, cash or UPINo
Materials, travel, overtimeDirectDirectNo

1. A percentage is not available to you

If the wage never passes through your system, there is no number to take a cut of. Commission is off the table by construction. The service charge therefore has to be a flat fee, tiered — by trade, by number of days, possibly by district. Put those tiers in admin configuration, not in code, because you will tune them repeatedly in the first six months.

2. Published wages have to come out of the product

daily_rate currently appears 95 times across 26 files — worker cards, booking summary, the existing payment screen, admin profile modal, the worker registration form, both Flutter apps and the Python worker backend model. This is not a one-line change and it should not be scheduled as one.

My recommendation is to keep the column and strip only the customer-facing surfaces. An indicative rate range is genuinely useful to admin when deciding which interested worker to assign, and to the worker as a profile field. Reword it in the registration form from "your daily rate" to "your indicative range", mark it admin-visible, and remove it from every customer view.

3. Charge at assignment, not at submission

The customer should not pay before they know they actually have a worker. Billing the moment admin assigns removes almost every refund case you would otherwise have to build and staff: if nobody takes the job, nothing was ever charged. The remaining refund paths are narrow — assigned worker no-shows, or the customer cancels before start — and both can be admin-triggered.

Practically: UPI through Razorpay is the right collection method for Kerala. UPI is typically zero-rated, cards and netbanking run around 2% plus GST — worth re-checking current rates before you commit, and worth nudging customers toward UPI in the payment screen.

4. The completion OTP no longer protects money

In an escrow model, OTP2 would gate the release of funds. Here the wage is cash between two people standing in a room, so it does not. Keep the OTP — it is still your proof of completion, your dispute evidence and your trigger for the ratings window — but stop thinking of it as payment protection, because it is not, and designing as though it is will lead to the wrong escalation flows.

The structural risk in this model is disintermediation. A one-time booking fee plus direct wage settlement gives both parties an obvious incentive to exchange phone numbers once and never book through you again. This is the single biggest threat to the business, not to the software, and it is worth designing against from day one: keep the fee low enough that evading it is not worth the effort; make repeat booking demonstrably faster than a phone call (saved sites, one-tap rebook of a known worker); attach the things they would lose by going direct — verified ratings, job history, dispute support, insurance if you ever add it — to platform bookings only; and track the repeat-booking ratio per worker as your early warning signal.
Still open: is there a worker-side charge too — registration fee, monthly subscription, or a per-job listing fee? You have only specified the customer side. It changes the worker onboarding flow, so worth answering before phase one.

13 — Dissent

Where I would push back

Five things. The first two decide whether this works at scale; the last three decide whether it holds together in the field.

  1. An admin gate on every single booking will not survive growth. At 20 bookings a day it is fine. At 200 it is a full-time job for a person who is asleep at 11pm when a customer books. Build the gates exactly as you described — but add auto-approval rules on day one: a returning customer, a standard job type, a value under some threshold, and a worker whose profile already matches the requirement all skip the queue and land in an audit log the admin reviews later. Same idea on assignment: if only one worker shows interest and they are qualified, auto-assign. Keep manual override always available.
  2. Do not notify every worker about every job. A plumber in Kannur receiving carpentry offers from Kollam will mute the app within a week, and then your dispatch stops working for everyone. Filter the broadcast by trade, district and availability, order by rating and distance, and give admin a "widen the broadcast" button for when a request goes unanswered. Supervisors and agents can reasonably get a wider feed than individual workers.
  3. Do not schedule the wage removal as a small task. 95 references across 26 files, spanning both Flutter apps, both React sites, the Node backend and the Python worker backend — including an existing payment_screen.dart built around a per-worker rate. Half-removing it is worse than not starting: a customer who sees a rate on one screen and negotiates a different number on site will file a grievance, and you will be arbitrating it.
  4. Kerala connectivity will break the completion step. A worker finishing in a basement or a rural interior with no signal cannot submit. The worker app needs an offline queue that stores the start and complete events with their timestamp and location, then syncs when signal returns — with the server trusting the recorded timestamp, not the arrival time.
  5. The revenue model is sound but leaky, and the leak is not technical. Covered in full in §9 — a booking fee with off-platform wages is the easiest model to launch and the easiest to route around. Build the retention hooks in the first version, not after you notice the repeat rate falling.

Locked 01 — Scope

Extend Crewzo as v2

No greenfield. Both Flutter apps, all three backends, the admin portal and the SMS gateway carry forward. The dispatch layer is added on top of the existing schema.

Locked 02 — Roles

Worker, agent and supervisor all take work directly

Seniority tiers rather than a delegation hierarchy. Same offer flow for every recipient; the tier affects broadcast priority and ordering, nothing else. This is the simplest of the options and it keeps job_offers flat.

Locked 03 — Broadcast

Filtered, with an admin widen button

Match on trade, district and availability. Order by rating and distance. Admin widens manually when a request goes unanswered, and gets alerted when the offer window expires with zero takers.

Locked 04 — Revenue

Flat service charge to the customer; wages off-platform

Crewzo bills a tiered booking fee, charged on assignment. Customer and worker negotiate and settle wages directly, and per-worker rates come out of every customer-facing surface. Worked through in §9.
